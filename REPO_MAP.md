# Repository Map

This repository is a Codex experimentation workspace.

Code generated here is reviewed manually before being movedto production research repositories.

This repository contains a research platform for developing and testing algorithmic trading models using **event-driven backtest data**.

The platform is designed to support **multiple strategies and predictive models** that share common utilities, data structures, and output conventions.

New models should **extend the existing structure** rather than introducing new architecture.

---

# Core Design Philosophy

The repository follows a consistent research pipeline:

```
raw data → cleaned data → engineered features → model training → evaluation → exported artifacts
```

Each model should follow this pattern.

Models should remain **modular and reusable** so that new strategies and predictive models can be added easily.

---

# Development Phases

The repository currently contains both research notebooks and partially
modularized code.

When using automated refactoring tools (such as Codex), follow this rule:

PHASE 1 — Notebook stabilization
    • Clean and standardize notebooks
    • Ensure reproducibility
    • Standardize paths via src/paths.py
    • Improve validation and robustness
    • DO NOT refactor notebooks into full pipelines yet

PHASE 2 — Pipeline refactor
    • Extract reusable logic from notebooks
    • Implement modular pipeline components under models/
    • Introduce orchestration modules if needed

Automated tools should assume the repository is currently in **Phase 1**
unless explicitly instructed otherwise.

---

# Important Rule for Automated Refactoring Tools

This document defines the **intended repository architecture**.

When refactoring notebooks or modules:

* Preserve the repository conventions defined here.
* Extend the architecture rather than redesigning it.
* Prefer reusing existing utilities and modules.
* Avoid introducing parallel frameworks or path systems.

---

# Path Management

All filesystem paths must be constructed using the centralized path definitions in:

```
src/paths.py
```

This module defines canonical path objects such as:

```
PROJECT_ROOT
DATA_RAW
DATA_INTERMEDIATE
OUTPUTS
MODELS
TABLES
FIGURES
NOTEBOOKS
EXPERIMENTS
```

Rules:

* Do **not hardcode absolute paths**
* Do **not construct user-specific paths manually**
* Always use the centralized path objects defined in `src/paths.py`
* All pipelines and notebooks must resolve paths through this module

This ensures that code runs correctly regardless of the machine or user environment.

# Main Directories

## models/

Contains the core logic for each trading model or predictive model.

Each model has its own namespace.

Example:

```
models/
    sancocho/
    regime_model/
```

Each model directory typically contains modules such as:

```
pipeline.py
features.py
target.py
train.py
```

Responsibilities:

| File        | Purpose                         |
| ----------- | ------------------------------- |
| pipeline.py | Orchestrates the full pipeline  |
| features.py | Feature engineering             |
| target.py   | Target construction             |
| train.py    | Model training and optimization |

Note:

Some models may initially exist as research notebooks.
Those notebooks are progressively **refactored into modular Python code** following this structure.

---

## data/

Stores datasets used by the pipelines.

Structure:

```
data/raw/
    Original input datasets

data/intermediate/
    Cleaned or transformed datasets used during model training
```

Each model should maintain its own namespace inside these directories.

Example:

```
data/raw/xls/input/regime_model/
data/intermediate/regime_model/
```

Rules:

* Raw data should **never be modified**
* Intermediate data may be regenerated by pipelines

---

## notebooks/

Contains research and orchestration notebooks.

Notebooks are used for:

* running pipelines
* exploratory analysis
* debugging
* generating figures
* reviewing outputs

Important rule:

Core business logic should ideally live in Python modules.

However, during early research phases, notebooks may temporarily contain
feature engineering, modeling, and optimization logic.

Automated tools should **not automatically extract notebook code into modules**
unless explicitly instructed to perform a pipeline refactor.

Reusable logic should live in Python modules under:

```
models/
src/
notebook_utils/
```

Notebooks should primarily act as:

* orchestration layers
* experimentation environments
* debugging tools

---

## notebook_utils/

Reusable utility library used across notebooks and models.

This package contains functions for:

* optimization
* feature transformations
* formatting and exports
* grid search utilities
* simulation utilities
* dashboard functions

Before creating new helper functions:

1. Check if functionality already exists in `notebook_utils`
2. Avoid duplicating utilities
3. Extend existing utilities when possible

---

## outputs/

Stores generated outputs from model runs.

Structure:

```
outputs/models/
outputs/tables/
outputs/figures/
```

Examples:

```
outputs/models/regime_model/round_1/
outputs/tables/regime_model/
outputs/figures/regime_model/
```

Artifacts may include:

```
model.pkl
feature_columns.pkl
model_metadata.json
```

Outputs are typically **ignored by Git**.

---

## experiments/

Optional directory for experimental work or temporary research runs.

Not all experiments need to become permanent models.

---

## src/

Contains shared reusable modules that are **not tied to a single model**.

Examples include:

* centralized path management
* shared infrastructure
* generic utilities

# Environment

All training runs inside the user's **Anaconda environment**.

Pinned dependencies:

```
scikit-learn == 0.20.3
xgboost == 0.80
pandas == 1.3.5
numpy == 1.19.2
```

Rules:

* Do **not upgrade packages without verifying compatibility**
* Do **not introduce APIs requiring newer versions**
* Maintain compatibility with this environment

# Model Pipeline Pattern

Every model should follow these stages:

1. Data ingestion
2. Data cleanup
3. Feature engineering
4. Target construction
5. Model training
6. Model optimization
7. Export artifacts

Artifacts must always be saved under:

```
outputs/
```

---

# Naming Conventions

Each model uses a unique namespace.

Example:

```
regime_model
```

Corresponding directories:

```
data/raw/xls/input/regime_model/
data/intermediate/regime_model/

outputs/models/regime_model/
outputs/tables/regime_model/
outputs/figures/regime_model/
```

This keeps artifacts organized and prevents cross-model conflicts.

---

# Validation Rules

All modeling must respect **time ordering**.

Allowed:

* chronological splits
* walk-forward validation

Not allowed:

* random train/test splits
* shuffled data
* leakage from future information

---

# Artifact Requirements

Every trained model should save:

```
trained model object (.pkl)
feature column list
model metadata
```

This ensures deterministic inference and compatibility with downstream models.

---

# Development Rules

Before writing new code:

1. Inspect the repository structure.
2. Identify reusable utilities.
3. Extend existing modules when possible.
4. Avoid duplicating functionality.
5. Preserve repository conventions.
6. Use centralized paths from `src/paths.py`.

The goal is to **extend the research platform rather than redesign it**.
